# design — add-game-craft

## 결정 1: 계층 경계는 **선언**이고, 검사기는 그 선언을 집행할 뿐이다

계층 이름과 금지 대상을 검사기가 알면 스택마다 lib 이 하나씩 는다.
검사기는 `{ layer, forbid }` 목록과 소스를 받아 위반만 낸다. **계층을 모른다.**

```json
{ "layer": "core", "forbid": ["package:flutter/", "dart:ui"], "why": "..." }
```

`layers.json` 에 엔진별 기본값을 둔다. 프로젝트가 다르면 호출자가 덮어쓴다.
`Ruling: 확장은 코드가 아니라 데이터로 받는다` 의 같은 적용이다.

## 결정 2: `why` 는 선택이 아니라 필수다

경계 위반 보고에 **왜 그 경계가 있는지**가 같이 나와야 한다.
"core 가 flutter 를 import 했다"만 오면 읽는 사람은 경계를 지우는 쪽을 택한다 —
경계는 언제나 당장은 불편하고 이득은 나중에 오기 때문이다.

ToonTone 이 이걸 정확히 해놓았다: *"이 경계가 무너지면 게임 규칙을 위젯 없이 테스트할 수
없게 되고, 규칙 변경이 느리고 불안정한 통합 테스트를 통과해야만 하게 된다."*

`why` 없는 경계 선언은 **던진다.** 조용히 통과시키면 이유 없는 경계가 쌓이고,
이유 없는 경계는 가장 먼저 지워진다.

## 결정 3: 경로 접두사로 계층을 판정한다 — 언어 파서를 넣지 않는다

`lib/core/...` 가 core 다. AST 를 파싱하면 언어마다 파서가 필요해지고
엔진 불가지론이 깨진다. import 줄은 **줄 단위 문자열 포함**으로 본다.

한계: 주석 처리된 import 도 잡힌다. 근사이고, **근사라고 표시한다.**
Luau 에는 import 문이 없어 `require(...)` 와 전역 접근(`game:GetService`)을 함께 본다 —
그래서 `forbid` 는 "import 경로"가 아니라 **"이 계층에 나타나면 안 되는 문자열"** 이다.

## 결정 4: 패리티는 다작 트랙에서만 게이트다

깊게 트랙(로블록스 한 게임)에는 플레이버가 없다. 거기에 패리티 게이트를 씌우면
있지도 않은 개념으로 막는다. `flavors` 가 비어 있으면 **위반 없음이 아니라 해당 없음**으로 낸다.

`Ruling: 미설정과 실패를 구분한다` · `Ruling: 도구 부재는 결함이 아니라 상태다` 의 같은 적용.
`applicable: false` 와 이유를 낸다. "검사해서 깨끗함"과 "검사 대상이 아님"은 다른 상태다.

## 결정 5: 패리티는 분기를 찾지, 플레이버 이름을 세지 않는다

플레이버 id 문자열이 코드에 나오는 것 자체는 위반이 아니다 — 설정을 읽는 코드는
당연히 id 를 다룬다. 위반은 **id 로 동작이 갈리는 것**이다.

그래서 "플레이버 식별자 + 비교 연산자"가 같은 줄에 있는 것을 찾는다:
`flavor == "x"` · `flavorId === 'y'` · `switch (flavor)` · `flavor != z`.

느슨한 쪽으로 틀리면 무해한 경고가 늘고, 빡빡한 쪽으로 틀리면 다작의 한계 비용이
조용히 올라간다. **놓치는 쪽이 더 나쁘므로** 애매하면 잡는다.
식별자 이름은 프로젝트마다 다르므로(`flavor` · `flavorId` · `variant` · `productFlavor`)
**데이터로 받는다.**

## 결정 6: craft 스킬은 엔진을 모른다

`level`·`narrative`·`gameux`·`asset`·`balance` 와 같은 규율이다
(`Ruling: 도메인 스킬은 엔진 불가지론이다`). 엔진별 금지 문자열은 `layers.json` 에 있고
스킬 본문은 **왜 그 경계가 있는지**와 **어떻게 설계하는지**만 담는다.

`tests/smoke/game-domain.test.ts` 의 엔진 토큰 검사에 `craft` 를 추가한다 —
선언만 하고 검사를 안 붙이면 다음 사이클에 바로 샌다.

## 결정 7: gameplay-engineer 는 build 를 대신하지 않는다

기존 에이전트 5종은 전부 산출물이 **문서·데이터**다(레벨 표·대사·팔레트·경제 수치).
gameplay-engineer 는 **코드**를 낸다. 그러면 `nereus:build` 와 겹칠 수 있다.

겹치지 않게 한다: 워크플로는 코어가 소유하고(`nereus:common`), gameplay-engineer 는
**게임플레이 코드의 판단**만 한다 — 어디까지가 순수 규칙이고 어디부터가 엔진 바인딩인가,
수직 슬라이스에 무엇을 넣고 무엇을 뺄 것인가, 무엇을 서버가 결정해야 하는가.
TDD 절차·게이트는 `nereus:build` 것을 그대로 쓴다.

## 측정 결과 (ToonTone, 2026-09-13)

| 검사기 | 결과 | 주입 검증 |
|---|---|---|
| `purity-check` (flutter 경계 3종 × Dart 137파일) | **위반 0** | 주입하면 2건 잡는다 |
| `parity-check` (플레이버 8종 × Dart 137파일) | **위반 0**, `applicable: true` | 주입하면 1건, `known: true` |

ToonTone `test/architecture_test.dart` 가 초록이고 헌법 원칙 VI 가 분기를 금지하므로
**0 이 나오는 것이 맞다.** 0 이 검사기 부작동이 아님을 위반 주입으로 따로 확인했다.

### 그 과정에서 잡은 오탐 두 부류

1. **문서 주석** — `lib/core/color/srgb_lab.dart:3` 의
   `/// 순수 계산만 하며 Flutter·dart:ui·I/O 에 의존하지 않는다.`
   **경계를 지키고 있다고 적은 문장이 경계 위반으로 잡혔다.**
   주석 줄을 건너뛴다. 블록 주석(`/* */`)은 안 본다 — 여는 줄만 보면 오탐이고,
   상태를 들고 가려면 문자열 리터럴과 구분해야 해서 파서가 된다.

2. **비교이지만 분기가 아닌 것** — 처음엔 "식별자 + 비교 연산자"로 봤더니 4건이 잡혔다:
   ```
   if (expected != null && pack.flavorId != expected)   변수 대 변수
   if (kindName is! String || flavorId is! String)      타입 검사
   if (flavor == null || packageName == null)           널 검사
   ```
   셋 다 갈리는 게 아니라 **같은 코드가 모든 플레이버에서 도는 모습**이다.
   비교 대상이 **문자열 리터럴**일 때만 잡는다. 리터럴이 알려진 플레이버면 `known: true`,
   아니어도 잡는다 — 목록이 최신이 아닐 수 있고 **놓치는 쪽이 더 나쁘다**.

두 오탐 모두 픽스처로는 안 나왔다. 실제 프로젝트에 돌려야 나오는 부류다.
